## 1 이 '현재 워크플로우' 의 불편함

(A) 부팅 템플릿을 매번 수동으로 복사 붙여넣기 해야함.

(B) 컨텍스트 열화를 수동으로 파악하고 handoff 문서를 작성한 뒤에 새 세션에서 수동으로 부팅 템플릿을 입력해야함

(C) 개발 현황을 github mobile 앱에서 요약되지 않은 채로 올라오는 pr들을 힘들게 파악해야함.

(D) 무인 개발 과정에서 운영자(나)의 결정이 필요한 경우 blocker가 발동되어서 선택지 UI가 제공되거나 턴이 일시정지 되는데, 내가 작업실에 없으면 계속 block된 상태가 유지됨

일단 (A)는 스킬로 만들어서 /init-orchestrate [추가할 디테일] 이런식으로 만들어두면 나중에 부팅 프롬프트가

```text

```

이런식으로 매우 편해질 것 같아. (B)는 어떻게 해결할지 잘 모르겠어 아직. 그리고 우리가 최종적으로 빌드할 개인 개발환경 인프라는 (C), (D)를 해결하기 위함이야.

## 2 (C) 해결- #pr-digest: 에이전트 대화를 사람이 읽을 수 있는 수준으로 압축

여기서 설계 철학이 중요해.

처음 생각하면:

```text
Worker ↔ Coordinator 대화
        ↓
전부 수집
        ↓
LLM이 계속 요약
        ↓
```

Slack

이라고 만들기 쉬운데, 나는 이렇게 만들지 않을 거야.

그렇게 하면 agent가 주고받는 수십 개 메시지를 실시간 요약해야 하고, 요약이 계속 바뀌고, 비용도 들고, 오히려 Slack이 시끄러워진다.

대신:

대화 자체가 아니라 "상태 변화"를 요약한다.

즉 다음 이벤트만 중요하다.

Worker 작업 완료

↓

PR 생성

Review Agent 검토

↓

승인 / 수정 요청

Worker 수정

↓

재검토

CI 통과

↓

Merge Ready

Coordinator merge

↓

완료

Orca orchestration 자체가 이미 이 방식과 잘 맞는다. Worker는 완료할 때 worker_done을 정확히 한 번 보내고, 현재 Orca 가이드도 그 body를 "무엇을 했고, 무엇을 발견했고, 무엇이 남았는지 3문장 요약" 형태로 보내도록 정의한다. 필요하면 coordinator가 완료 이후에도 worker-read로 해당 worker의 실제 transcript를 읽을 수 있다. GitHub

따라서 Slack Observer가 모든 대화를 훔쳐보며 계속 요약할 필요가 없다.

### 2.3 #pr-digest를 누가 만들어야 하나?

이기 때문이다.

매 단계마다:

Slack용 예쁜 요약도 하나 만들어.

를 시키면 orchestration context에 쓸데없는 책임을 추가한다.

따라서 별도 프로세스를 만든다.

가칭:

orca-slack-bridge

이 프로그램은 Agent가 아니다.

```text
┌──────────────────────────────┐
│ orca-slack-bridge            │
│                              │
│ Orca 상태 관찰               │

│ 필요한 정보만 수집           │
│         ↓                    │

│         ↓                    │

```

즉 Observer다.

Worker와 coordinator 사이에는 끼어들지 않는다.

### 3.1 그런데 Coordinator가 판단할 수 없는 상황 발생

예를 들어 backend worker가 이런 문제를 발견한다.

Coordinator도 코드와 문서로 결정할 수 없다.
