# 작업 규약

이 문서는 `dev-infra`의 문서 작성, 설계, 구현, 디버깅, 검증 세션에 공통으로 적용되는 운영 규약이다.

## 협업 방식

- 이 프로젝트는 “빠른 결과물”이 아니라 “사용자가 이해하고 검증한 결과물”을 목표로 한다.
- 확신이 없으면 진행하지 않고 질문한다. 추측으로 메우지 않는다.
- 사용자의 판단에 동의하지 않으면 명시적으로 반대하고 근거를 제시한다. 동의를 위한 동의를 하지 않는다.
- 사용자가 방향을 정하기 전에는 코드를 쓰지 않는다. 먼저 접근법을 제안하고 합의한다.

## 변경 절차

모든 변경은 다음 순서를 따른다.

1. 무엇을 왜 바꾸는지 한 문단으로 설명한다.
2. 영향 범위와 건드리는 파일·호출자를 밝힌다.
3. 기존 구조·네이밍·스타일을 유지하며 최소 diff로 구현한다. 요청하지 않은 리팩터링을 하지 않는다.
4. 각 변경에 한 줄 근거를 남긴다.

## 디버깅 절차

예외 없이 다음 순서를 따른다.

1. 원인 가설을 먼저 진술한다.
2. 그 가설을 반증할 관측을 진술한다.
3. 그 관측을 실제로 수행하고 결과를 제시한다.
4. 가설이 확인된 뒤에만 수정한다.

원인을 설명하지 못하는 수정은 금지한다. 특수 케이스 분기로 증상만 없애지 않는다.

두 번 연속 수정이 실패하면 멈추고 다음을 보고한다.

- 지금까지 배제된 것
- 남은 가설

## 검증

- “동작합니다”라고 말할 때는 실행 명령과 출력을 함께 제시한다.
- 실행하지 않았다면 “실행하지 않았음”이라고 명시한다.
- 테스트 없이 완료를 선언하지 않는다.

## 컨텍스트

- 파일 내용을 기억에 의존해 답하지 않는다. 필요하면 다시 읽는다.
- 앞에서 기각된 접근을 다시 제안하지 않는다.
- 컨텍스트가 부담스러워지면 먼저 알리고 handoff 문서를 제안한다.

## 금지

- 요청 범위를 넘는 변경
- 사용하지 않는 추상화와 조기 일반화
- 근거 없는 성능·정확성 주장

## Agent orchestration에 대한 적용

- coordinator는 이 규약을 worker와 reviewer에게 전달하고, 각 작업의 수용 기준에 반영한다.
- handoff에는 실패한 수정 횟수, 배제된 가설, 실행한 검증과 실행하지 않은 검증을 남겨 successor가 같은 오류를 반복하지 않게 한다.
- 문서의 `TBD`를 구현 편의를 위해 임의 확정하지 않는다.
